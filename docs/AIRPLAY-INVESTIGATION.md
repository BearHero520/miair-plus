# AirPlay 无声排查（2026-09-14）

本次发现并修复了可复现的程序缺陷，但未连接用户 NAS 或 Apple 发送端，因此不能将模拟复现等同于已确认用户现场根因。

## 已复现：音量请求阻塞音频接收

传统 AirPlay 的 RTSP `SET_PARAMETER volume` 原来同步调用小米云。音量接口慢时，RTSP 主循环不能继续读取 TCP 音频，也不能及时回复发送端。`RECORD` 同时开始等待音频，5 秒没有生成 4096 字节转码输出就取消整个会话。

回归测试模拟两次音量请求、每次云响应 4 秒：修改前在约 5 秒时记录“等待转码音频超时”，生成字节为 0，第二次请求返回 500，播放未启动。修改后音量请求及时应答，最新音量由独立工作协程同步，音频接收与转码继续运行，播放正常启动。工作协程串行处理音箱操作、合并尚未执行的音量更新，并随会话取消。

## 音量处理缺陷

- 传统 AirPlay 的最低非静音音量（例如 -30 dB）原来取整为音箱 0%。现保留最低 1%，显式静音仍为 0%；音量查询返回会话中的音量，不再固定返回 0 dB。
- `StartAirPlay` 原来只发送播放地址，没有像 DLNA 一样应用音箱音量。AirPlay 2 的软件增益不会解除音箱硬件的零音量。现应用渲染器中的音量，并保留显式静音；设置失败记录独立警告。

## 验证与未证实项

- 真实 FFmpeg 8.1：按每包 352 个采样的实时速率输入 ALAC，普通音频和静音输入均约 0.37 秒达到 4096 字节 MP3 启动门槛。本环境未复现 FFmpeg 探测缓冲导致的 5 秒超时。
- 真实 RTSP/TCP、RTSP/UDP 会话，慢云响应模拟，UDP 的 RSA 密钥协商及 AES 音频解密。
- HTTP 客户端读取实时 MP3，再用 FFmpeg 解码为非零 PCM，验证的是实际输出内容，不只是“已发送播放指令”。
- 之前修正的 Range 416 行为确实会拒绝某些探测请求，但没有现场 HTTP 请求证明用户音箱遭遇了这一情况。
- 对照本地 miair-next，它的音量回调已经异步提交，不能据“症状一样”断言两个项目是同一个根因。
- 核对 Shairport Sync 5.5.1 的 [stdout 后端](https://github.com/mikebrady/shairport-sync/blob/5.5.1/audio_stdout.c) 与 [音频选项解析](https://github.com/mikebrady/shairport-sync/blob/5.5.1/audio.c)：当前配置显式选择 S16_BE / 44100 Hz / 双声道，与 Go 端 PCM 解码格式一致。此次没有在 Linux 上重新运行原生接收器或验证 Apple 配对、PTP 时钟及现场组播网络。

## NAS 实测判定

安装含修复的版本后，记录一次投送：收到会话 → 转码就绪 → 音箱播放/音量操作 → 播放器开始拉流 → 发送字节。只有结合此记录、音箱型号、使用的是传统 AirPlay 还是 AirPlay 2，以及音箱实际发声情况，才能确认现场问题是否消失。当前本地旧记录只有开发预览启动信息，没有可用于归因的 NAS 投送日志。
